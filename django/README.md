# django

Learning log for the Django stage of this repo. Unlike the other stage
READMEs (which describe *finished* code), this one is a running journal
of what's being learned and why, updated as the material progresses -
see [CLAUDE.md](../CLAUDE.md)'s "Keeping docs in sync" section for that
distinction.

## The idea

Django is a batteries-included Python web framework: ORM, admin site,
templating, routing, and forms all ship together and are meant to be
used as a matched set, unlike Flask's minimal-core-plus-extensions
approach seen in [data-serve](../data-serve/README.md). Working through
it here as a comparison point against that stage.

The example project is a movie review site (`moviereviews`), built up
app-by-app as the book/curriculum introduces new Django concepts.

## Setup

Django is a normal repo-root dependency, same as every other Python
stage - see the root [README.md](../README.md#python-setup) for the
shared `.venv` + pip-tools workflow. No stage-specific virtual
environment.

```
    news/                  # app: news listing (generated by `startapp news`)
      models.py             # News
      views.py               # index
      admin.py
      urls.py                 # news's own routes, included via moviereviews/urls.py's include('news.urls')
      templates/news/          # index.html (extends movie/base.html)
      management/commands/     # seed_news.py
      migrations/
    accounts/              # app: signup/login/logout (generated by `startapp accounts`)
      forms.py               # SignUpForm, LoginForm - Bootstrap-styled subclasses of Django's inbuilt auth forms

      urls.py                 # included via moviereviews/urls.py's include('accounts.urls')
      templates/accounts/      # signup.html, login.html (extend movie/base.html)
      # no models.py content, no migrations - uses Django's built-in User model
```

Created from the repo root with:

```bash
cd django
python -m django startproject moviereviews
```

(`python -m django` rather than a bare `django-admin` command, since
Django is only installed inside this repo's `.venv`, not on the system
`PATH`.)

Kept as Django's own generated layout rather than being forced into
this repo's usual flat-stage shape (see
[docs/python-implementation.md](../docs/python-implementation.md)'s
"Project layout within a stage" section) - same reasoning as
`data-scrape/pokemon_scrapy/` for Scrapy: following the framework's own
convention is more legible to anyone who already knows it.

- **2026-08-28** - swapped the plain-text `HttpResponse`s for real
  templates, and passed data into them:
  - Templates live under `movie/templates/movie/` - the extra nested
    `movie/` (app name repeated) is Django's "app-namespaced" template
    convention: with `APP_DIRS: True` (the `startproject` default, see
    `moviereviews/settings.py`), every installed app's `templates/`
    folder is searched as one flat pool, so two apps' `home.html` would
    collide without the extra per-app subfolder to disambiguate.
  - `base.html` is a shared shell (nav bar + CSS) with a `{% block
    content %}`; `home.html`/`about.html` do `{% extends "movie/base.html"
    %}` and only fill in that block - avoids repeating the `<head>`/nav
    markup on every page.
  - **Gotcha hit while writing `base.html`**: an explanatory comment
    used HTML's `<!-- -->` syntax but happened to spell out
    `{% block content %}` as literal text inside it. Django's template
    lexer scans for `{% %}`/`{{ }}` tags everywhere in the file,
    including inside HTML comments - it doesn't know HTML comment
    syntax at all - so that counted as a second `content` block and
    Django raised `TemplateSyntaxError: 'block' tag with name 'content'
    appears more than once`. Fixed by using Django's own comment syntax
    (`{# ... #}`) for anything that needs to mention a tag name, since
    HTML comments aren't safe for that here.
  - `movie/views.py`'s `home`/`about` now call
    `render(request, "movie/home.html", {"name": "Xuan Vinh"})` (and
    the `about.html` equivalent) instead of returning `HttpResponse`
    directly. The dict is the template's *context* - each key becomes a
    `{{ variable }}` the template can use, which is how the page prints
    "Hi Xuan Vinh, thanks for stopping by!".
  - Verified by running `manage.py runserver` locally and curling `/`
    and `/about/` - both render the styled page with the name filled
    in.

  logged-in users and, for edit/delete, to the review's own author:
  - New model `Review` in `movie/models.py` - `movie` (`ForeignKey` to

    specified) made so "edit your review" is always unambiguous. Ran

    movie than the page they're actually on.

    `@login_required` (Django's built-in) - the *authentication* half
    of authorization, "is anyone logged in at all":
    - `add_review(movie_id)` - if `request.user` already has a review
      on this movie (checked before rendering the form), redirects to
      `edit_review` for it instead of risking a
      `unique_together`-rejected duplicate insert.
    - `edit_review(review_id)` / `delete_review(review_id)` - both add
      the *authorization* half that actually matters: `if review.user
      != request.user: return HttpResponseForbidden(...)`. Being
      logged in only proves someone is signed in, not that they own
      *this* review - without this check, any logged-in user could

      URL. `delete_review` also only deletes on `POST`, showing a
      confirm page on `GET` - same "no destructive action on a bare

      the view), not the movie's, and their literal `reviews/` prefix
