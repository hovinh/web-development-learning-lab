The moment every analysis hits

  • A chart in a notebook convinces you.
  • It rarely convinces a colleague who is never going to open that notebook.
  • A small web app can: move a slider, filter to their own region, type a value and watch the model's answer change.
  • That feels very different from a screenshot.
[~2 min] Open with the everyday moment - this is the 'why' before any tooling talk.

Where this quietly pays off

  • Makes exploring a dataset more interactive
  • Demonstrates a model as a live service
  • Prototypes a product idea before anyone spends engineering time on it
  • An LLM can write most of the boilerplate for you now
  • …but the difficulty didn't disappear. It moved: to picking the right tool.

Two easy things to miss

  • Tailwind isn't a rival to Django or React - it only styles, so it works with any of them.
  • React and Angular sit on the same rung: both still need something else to supply data and handle login.
  • If you live in Python: Streamlit and Dash need zero JavaScript, and for many tasks that's the whole answer.
[~2.5 min] These two misconceptions cause most of the 'framework wars' confusion.

Stop asking 'which framework?'

  • Ask instead: what does this app actually have to do?
  • Any web app is some combination of the same 12 capabilities.
  • Tick the rows your use case needs - the ticks are the decision.

Multi-user: six things to solve

  • Authentication — who is this user?
  • Authorization — what may they do?
  • Data isolation — user A never sees user B's rows
  • Per-user state, concurrent writes, and an audit trail
  • None of this shows up in a 'build a dashboard in 10 minutes' tutorial.
[~2.5 min] This and background jobs are the two gaps that bite the moment a demo becomes a product.

[~2.5 min] The rule to repeat: authorization is enforced on the server. Hiding a button in React protects nothing. Streamlit's cache is shared across all users.

WEB IS SECONDARY HERE

An LLM makes writing the code cheap. That makes the choice of what to write - and who owns the logic - the one part worth your care.

[~2.5 min] This is the thesis of the whole talk, not just the blog's closing line. Everything before this was building the vocabulary to make that choice well.

Let the LLM write boilerplate. You hold the backend logic.

  • ✅ 'Write a Django view that filters by request.user' — you already decided the ownership rule
  • ✅ 'Scaffold this FastAPI route from my Pydantic model' — you own the model
  • 🚫 'Build me a labeling tool' and walking away — now the LLM decided your data model, your auth, your schema
  • The 12-functionality list is exactly how you stay the one deciding, not just the one asking
  • If everything is LLM-driven end to end, you stop being able to explain your own codebase
[~2.5 min] Land this before the head-to-head comparison - it reframes why the Django-vs-FastAPI contrast coming up matters beyond 'which is prettier'.

The test case: a labeling tool

  • A model has predicted a category for a batch of support tickets.
  • Reviewers label rows; admins see everyone's labels and manage users.
  • A reviewer sees only the rows assigned to them.
  • A long job re-scores the data with a new model.
  • That touches almost all 12 functionalities — a fair test.
[~2 min] Set up the comparison before showing the table.

Same guarantee, two very different bills

  • Django: less code, an admin for free, a queryset filter for the hard part
  • FastAPI + React: more code, but an instant, keyboard-driven feel and a separate API other systems can call
  • Start with Django, outgrow it, add an API and put React in front later — you don't have to throw away the data model
