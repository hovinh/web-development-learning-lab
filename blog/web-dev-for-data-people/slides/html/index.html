let-llm-write.md

Let the LLM write the code. You decide the rules.

  • 🚫 “Build me a labeling tool.” The LLM quietly picks the tool, what gets saved, and who can see what

  • Skip it, and you end up with an app you can't explain, check, or safely change

three-easy-things.md

Three easy things to miss

  • Tailwind (styling only) isn't a rival to Django or React - it works with either.
  • React and Angular are alternatives to each other, and neither works alone: both need a server behind them for data and login.
  • If you live in Python: Streamlit and Dash need zero JavaScript, and for many tasks that's the whole answer.
[~2 min] These cause most of the 'framework wars' confusion. Keeping the map on screen means nobody has to hold these names in their head.

multi-user-six.md

Multi-user: six things to solve

  • Authentication (#9) — who is this user?
  • Authorization (#10) — what may they do?
  • Data isolation (#10) — user A never sees user B's rows
  • Per-user state (#11) — remembering each user's own choices
  • Concurrent writes (#7) — two people editing the same row at once
  • Audit trail (#7) — who changed what, and when
  • Don't count on an LLM to add these unprompted: name each one you need.
[~2.5 min] This and background jobs are the two gaps that bite the moment a demo becomes a product. The numbers show they're not new functionalities - they're what #7, #9-11 really mean once more than one person uses the app. None of this shows up in a 'build a dashboard in 10 minutes' tutorial.
tools-differ-sharply.json

The tools differ sharply here

ToolWhat you get
DjangoAuth, sessions, groups & permissions (role-based access) - all built in
FlaskNothing built in - Flask-Login adds sessions; roles you write yourself
FastAPINothing built in - docs show an OAuth2/JWT pattern (a token sent with every request) to write yourself
StreamlitBuilt-in OIDC login (“log in with Google/Microsoft”) - but no roles, and cached data is shared by every user
Dashdash-auth: HTTP Basic only (a plain browser login popup, no real session) - no logout
React, AngularLogin screens only - real security lives on the server

→ Only Django ships real roles. With anything else, your request has to spell out who may see and change what.

[~2.5 min] The rule to repeat: authorization is enforced on the server. Hiding a button in React protects nothing. Streamlit's cache being shared means one user's filtered data can be served to another if you cache per-user results.
web-page-must.md

A web page must answer in seconds. Retraining a model doesn't.

[1]
Clicking 'Start' starts the job — the page gets a job id back at once
[2]
The job runs somewhere else — in a separate worker process
[3]
Its status is stored — a row in a table, updated as it runs
[4]
The page checks back — every few seconds, until it's done

→ Ask for this shape by name: “run it as a background job, and have the page poll its status.”

[~2 min] The fix is always this same shape. This exact sequence reappears in demo 3.

views.py

The rule you own, in two codebases

Django · labeling/views.py
@login_required                 # login: built in
def queue(request):
    Item.objects.filter(assigned_to=request.user)

@login_required
def label_item(request, item_id):
    get_object_or_404(Item, pk=item_id,
                      assigned_to=request.user)

# The rule is part of each query itself -
# there's no separate guard to forget.
FastAPI · api/deps.py + api/main.py
def get_owned_item(item_id, current_user, db):
    ...filter(Item.assigned_to_id == current_user.id)

@app.get("/items")                  # 1: a list can't
    ...filter(Item.assigned_to_id    #    reuse the guard
              == current_user.id)

@app.get("/items/{item_id}")        # 2: remember to
    item = Depends(get_owned_item)  #    attach it

@app.post("/items/{item_id}/label") # 3: ...and here
    item = Depends(get_owned_item)

# plus security.py: JWT login, by hand

→ You don't have to write this line. You do have to know it exists - and ask for the test that proves it.

[~2.5 min] Abridged from the two demos' real code. Same rule both times. In Django the rule sits inside the query; in FastAPI a route that forgets Depends(...) still runs fine and quietly returns someone else's rows. Both demos ship a test that logs in as alice and asks for bob's item - that test is what you ask the LLM for.
same-guarantee-two.md

Same guarantee, two very different bills

  • The guarantee: a reviewer never sees another reviewer's rows - both stacks deliver it
  • Django: less code, an admin for free, the rule inside one query per view
  • FastAPI + React: more code, but an instant, keyboard-driven feel and a separate API other systems can call
  • Start with Django; add an API and React later without throwing away the data model
  • Either way, the LLM wrote most of the code. The request is where the two diverged.

takeaways.md

Takeaways

  • You'll ask an LLM to build it. The request - which tool, which rules - is the part you own
  • Decompose before you choose: tick the 12, then start at the lowest rung that covers your furthest tick

backup-get-best.md

Backup: can I get the best of both worlds?

  • Yes - and it's the normal path, not a special trick.
  • Start Django. Add Django REST Framework once another system (or a future React frontend) needs an API - the data model doesn't change.
  • Put React (or just htmx/Alpine.js, no build step) in front of only the screens that must feel instant - label review, not the admin.
  • django-ninja is a lighter, FastAPI-flavored alternative to DRF if you want typed, automatic-docs endpoints without leaving Django.
  • What you don't get: two frameworks' auth merged into one - you still pick a single system of record for who's logged in.
[~0 min] Only show this if asked - it's the natural 'can't I have both' follow-up. The honest limit: authentication still has to live in one place.
